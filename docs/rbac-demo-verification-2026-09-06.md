# Demo RBAC 实测、修复与发布说明

日期：2026-09-06。代码基准：`a8e8cd284ee016aaa280f58ad36eb4b6709e3abc`，在已有未提交 V2 变更上增量修复。通过 Kimi WebBridge 使用真实浏览器访问用户指定的 `https://www.honesttai.com/app/`，不是抓静态 HTML 代替交互。

## 线上观察与问题来源

- 当前浏览器登录身份为系统超管。使用页面实际填写并提交新增成员，`POST /api/users` 返回 **201**，因此“创建接口对所有账号都失败”并不成立。
- 默认机构的授权上限没有 `page.members` 和 `members.manage`，已有机构管理员角色同样缺少对应授权。普通用户不能仅凭“机构管理员”这个名称获得权限；超管不受该机构权限上限限制。**没有擅自恢复/扩大默认机构的授权。**
- 新建独立测试机构后，默认管理员角色包含成员页面和管理权限；这与现有默认机构配置不同，不能把两者混为系统角色初始化故障。

## 关键复现与本地修复对照

| 用例 | Demo 修复前结果 | 修复后的本地真实 API |
| --- | --- | --- |
| 超管通过 UI 创建成员 | 201 | 201；默认稳定只读角色、默认不分配客户 |
| 重复邮箱 | 500，泄漏 PostgreSQL 唯一约束名 | 409，说明账号已存在；停用账号提示恢复 |
| 受限成员管理员创建更高权限账号 | **201** | **403** |
| 相同角色但授予全部客户、扩大客户范围 | **201** | **403**；有权限的范围内可正常创建 |
| 受限成员管理员停用高权限成员 | **200** | **403**；恢复/重置密码同样受约束 |
| 显式 `roleIds: []` | 被静默替换为只读角色 | 明确保持无角色；UI 新建仍要求至少选一个角色 |
| 默认角色改名后省略 roleIds | 201，但账号没有角色 | 通过稳定 `system_key` 找到改名后的角色 |
| 跨机构角色 | 拒绝，但返回 500 | 400，事务回滚 |
| 给机构角色加入系统专用权限 | 拒绝，但返回 500 | 403 |
| 删除仍有成员的角色 | 拒绝，但返回 500 | 409，并在事务内锁定角色防并发丢授权 |
| 收回后恢复机构授权上限 | 角色权限被永久删除，恢复上限仍缺权限 | 角色定义不变，撤权立即生效，恢复上限重新取交集 |
| 角色撤权与重新授权 | 现有 token 下立即生效 | 保持；前端定期/聚焦刷新身份，避免菜单长时间停留在旧授权 |
| 可见项目 / 同机构未授权项目 | 200 / 404 | 保持 |
| 只读成员修改角色 | 403 | 保持 |
| 封禁机构 / 解封后的旧 token | 401 / 仍 401 | 保持；解封不复活旧登录会话 |
| 停用后恢复、密码重置 | 无完整恢复/重置入口 | UI 与 API 可用；旧密码 401、新密码 200；旧会话撤销 |

测试中 `GET /api/users` 是否允许取决于角色是否有 `page.members`。新机构只读角色可能具备成员只读页面，而旧默认机构角色没有；200 不代表跨机构读到了用户。真正的数据隔离仍由活动机构和客户范围判断。

## 修复范围与契约

### 服务端

- `apps/worker/src/member-access.ts` 从数据库重新解析操作者权限，在事务内限制可授予的角色和客户；HTTP 创建、停用、恢复、重置密码都传入已认证操作者。不能靠传入 `role:admin`、角色 ID 或 `allProjects:true` 提升权限。
- `auth.ts` 处理邮箱 trim/大小写重复、友好 409、默认无客户、稳定默认角色、空角色不回退；域审计记录操作目标和授权范围，不包含密码。
- `rbac.ts` 将机构授权作为上限，不再删除角色定义；角色新增/改名冲突有清晰提示，删除和成员授权使用事务/锁。重复默认初始化不会重新授予被撤销的权限。
- `POST /api/auth/password` 允许已登录账号验证当前密码后修改自己的密码，并撤销其他会话；该路径不依赖业务角色。错误尝试有界限流。
- `GET /api/users/options?kind=roles|projects`：需要 `members.manage`，分页、搜索只返回可分配角色/可见客户以及 `allProjectsAllowed`。不是截断第一页后假装没有更多角色。
- `POST /api/users/:id/restore` 与 `POST /api/users/:id/password`：需要 `members.manage`，且目标不能是系统超管、自己或权限/范围高于操作者的成员。恢复不恢复旧 token，重置撤销全部会话。

### 前端

- 成员创建具备 loading、防重复提交、独立错误提示、可搜索/翻页的授权选项、多角色和客户范围；不再按服务端排序取第一个角色默认为授权。
- 无成员管理权限显示明确只读提示，不展示一个无法操作的创建表单；系统超管行标记保护，当前账号与越权目标不显示可执行管理按钮。
- 成员列表支持搜索停用账号、恢复和重置密码；账号区新增验证旧密码的修改密码入口。
- 权限编辑保留跨页角色与客户选择，分页不会重载并覆盖机构授权草稿；被上限临时禁用的角色权限有提示且不被普通勾选静默丢弃。
- 通用分页失败被显式记录、可重试；过期响应不能覆盖新结果。身份每 15 秒以及窗口聚焦时刷新；新建客户先更新自身范围，避免受限创建者立刻被前端旧范围拦截。

## Migration 与发布

新增 `0020_membership_rbac.sql`：新增默认角色稳定键及唯一索引、新成员默认客户范围改为 false、登记候选/恢复/重置 API 策略并更新权限标签。已有用户客户范围和角色授权不自动改变；未知的历史改名角色不会按猜测授予默认身份，用户应明确选择角色。

本次没有部署 Demo。部署必须先应用包含 V2 和 RBAC 的完整服务端迁移/代码，再更新 Web；正式桌面客户端也需带上新版 Web。新前端依赖 `/api/users/options` 等端点，不应只发布前端。

如果要让 Demo 现有机构管理员可创建用户，需要超管明确为默认机构开启 `page.members`、`members.manage`，并为对应角色配置这两项；按实际需要分配客户范围。角色名本身不是权限，不建议用“全部授权”掩盖配置问题。

## 测试隔离和清理

线上只使用 `RBAC验收-20260906-隔离测试` 机构及明确命名的测试资源。创建了 8 个临时账号（含默认机构的一个页面复现账号）、两个草稿测试项目及一个自定义角色；未采集、未调用模型、未写入客户证据。

结束后 8 个账号全部成功停用，测试机构已封禁封存，活动机构恢复为 `default`；原有客户和成员权限未改动。保留测试审计，不声称删除了所有记录。

本地使用新建独立 PGlite、真实 API 与构建后的 Web，通过同一 WebBridge 分组交互验证创建/重复/停用/恢复/重置。自动化回归覆盖授权边界、默认角色改名、空角色、邮箱冲突、会话撤销、跨租户、机构上限恢复和超管保护。不连接或迁移线上 PostgreSQL。

线上复现与本地回归不是“修复已上线”；真实 PostgreSQL 并发和更新后的线上回归须在发布后完成。
